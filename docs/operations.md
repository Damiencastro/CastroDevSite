# Operations

How this site is built, deployed, and configured today.

This document describes the current state only. Known weaknesses and planned changes are tracked in [security-audit.md](security-audit.md).

Last verified against the repository, GitHub, and Firebase on 2026-11-11.

## At a glance

- **Repository:** `Damiencastro/CastroDevSite` on GitHub, public
- **Firebase project:** `castrodevwebsite`, set in [.firebaserc](../.firebaserc)
- **Live site:** <https://castrodevwebsite.web.app>, <https://damiencastro.dev>
- **Database:** Cloud Firestore, `(default)` database, native mode
- **Build:** `ng build`, with output in `dist/castrodevwebsite/browser`
- **CI/CD:** two GitHub Actions workflows in [.github/workflows](../.github/workflows), running on Node 24

## How a change reaches production

1. Push a branch and open a pull request against `main`.
2. The PR workflow builds the site and deploys it to a temporary **preview channel**. The Firebase action comments the preview URL on the PR.
3. Merge the PR. The push to `main` triggers the merge workflow, which builds again and deploys to the **live channel**.

A direct push to `main` skips steps 1 and 2 and deploys straight to production. `main` has no branch protection or rulesets, so nothing prevents this.

A full run takes 30 to 60 seconds.

## The workflows

Both files were generated by `firebase init hosting:github` and later edited to add the environment file step. They run the same five steps:

1. **`actions/checkout@v4`** checks out the commit.
2. **`actions/setup-node@v4`** installs Node 24 and restores the npm cache.
3. **Create production environment file** writes `src/environments/environment.production.ts` from six repository secrets. The file is gitignored, so it only ever exists inside the CI runner.
4. **`npm ci && npm run build`** installs exact versions from `package-lock.json`, then runs a production build. The production configuration in [angular.json](../angular.json) swaps `environment.ts` for the generated file.
5. **`FirebaseExtended/action-hosting-deploy@v0`** uploads the build output to Firebase Hosting, authenticating with the service account secret.

Neither workflow runs the tests, a linter, or a dependency audit.

The two differ in when they run and where they deploy:

| | Pull request workflow | Merge workflow |
| --- | --- | --- |
| File | [firebase-hosting-pull-request.yml](../.github/workflows/firebase-hosting-pull-request.yml) | [firebase-hosting-merge.yml](../.github/workflows/firebase-hosting-merge.yml) |
| Trigger | Any pull request | Push to `main` |
| Deploys to | A preview channel named after the PR, such as `pr2-styling` | The `live` channel |
| Token permissions | `checks: write`, `contents: read`, `pull-requests: write` | Not declared, so the repository default applies |
| Fork PRs | Skipped by the `if:` condition, because forks do not receive secrets | Not applicable |

## Secrets and configuration

The workflows reference seven repository secrets, found under Settings → Secrets and variables → Actions. The names below come from the workflow files. The CLI token on this machine is not allowed to list secrets, so their presence is confirmed only by the fact that recent deploys succeed.

**Deploy credential**

- `FIREBASE_SERVICE_ACCOUNT_CASTRODEVWEBSITE` is the JSON key for the Google service account that deploys to Hosting. This is the one sensitive value: anyone holding it can deploy to the site and use whatever other roles the account has.

**Firebase web config**

- `FIREBASE_API_KEY`
- `FIREBASE_AUTH_DOMAIN`
- `FIREBASE_PROJECT_ID`
- `FIREBASE_STORAGE_BUCKET`
- `FIREBASE_MESSAGING_SENDER_ID`
- `FIREBASE_APP_ID`

These six are not sensitive. They are compiled into the JavaScript bundle and sent to every visitor. A Firebase API key identifies the project; it does not grant access. Access to data is decided by Firestore security rules.

`GITHUB_TOKEN` is also used. GitHub creates it automatically for each run, so there is nothing to manage.

## Firebase

### Hosting

[firebase.json](../firebase.json) configures hosting only:

- `public` points at the Angular build output.
- A catch-all rewrite sends every path to `/index.html`, so deep links such as `/blog/some-post` load the app and let the Angular router take over.
- No custom response headers are set. The live site sends `Strict-Transport-Security`, which Firebase adds by default, and `Cache-Control: max-age=3600`.

Each pull request gets its own preview channel, which expires seven days after its last deploy. That is the deploy action's default. On the verification date there were two, `pr1-dependency-update` and `pr2-styling`, both expiring 2026-11-16. The `live` channel never expires.

### Firestore

Firestore is configured in the app but not yet used. [firebase.service.ts](../src/app/core/services/firebase.service.ts) defines reads for two collections, `blogPosts` and `projects`, but no page calls it. The blog and portfolio pages show static placeholder content. The app has no sign-in, so any read it does make will be anonymous.

Firestore security rules are not in this repository. They exist only in the Firebase console.

An anonymous read of either collection currently returns `403 PERMISSION_DENIED`. The rules therefore deny public reads. Nothing on the live site is affected today, but the rules will need to allow reads on those collections before any page can use them.

## Local development

`ng serve` uses the development configuration, which has no file replacement, so it loads the committed [environment.ts](../src/environments/environment.ts) with its `YOUR_API_KEY` placeholders. Every page works, because none of them reads Firestore yet. Once a page does, it will fail locally until real config is supplied.

To build for production locally, copy `environment.ts` to `src/environments/environment.production.ts` and fill in the real web config from the Firebase console (Project settings → Your apps). That file is gitignored.

## Common tasks

### Preview a change

Open a pull request from a branch in this repository. The preview URL appears as a PR comment.

### Deploy to production

Merge to `main`.

### Roll back a bad deploy

There are two ways:

- **Firebase console (fastest).** Go to Hosting → Release history, select the last good release, and choose Roll back. This changes what is served without touching git, so `main` still contains the bad commit. Follow up with a revert.
- **Git.** Run `git revert` on the bad commit and push to `main`. The merge workflow deploys the reverted state.

### Rotate the deploy key

1. In Google Cloud console, go to IAM & Admin → Service accounts and open the GitHub Actions account.
2. Under Keys, create a new JSON key.
3. Paste it into the `FIREBASE_SERVICE_ACCOUNT_CASTRODEVWEBSITE` secret on GitHub.
4. Confirm that a deploy succeeds.
5. Delete the old key.
